# 계정 발급과 인증

> 초안 (리뷰 대기). 사내 B2B 전제: 로그인하는 사람은 **사원**뿐이다. 고객(대리점·법인)은
> 로그인하지 않으며 order 서비스의 거래처 데이터로만 존재한다 (이 명세 범위 밖).

## 목적

사원 계정의 생애주기(발급 → 활성화 → 로그인 → 비활성)와 토큰 발급·검증을 정한다.
계정은 **관리자가 발급**하고(자가 회원가입 없음), 사원은 발급받은 계정을 **활성화**만 한다.
역할(role)은 관리자가 발급 시점에 정하며, 사원이 스스로 고를 수 없다.

### 이번 범위

- 관리자 계정 발급 (사번·이메일·역할 입력)
- 활성화: 이메일로 받은 **일회용 링크**로 비밀번호 설정
- 로그인·토큰: JWT Access(RS256) + Refresh(Redis, 회전)
- 역할 기반 접근 제어 (admin 전용 API)

### 범위 밖 (이번에 안 함)

- 비밀번호 재설정(찾기)과 6자리 이메일 코드 — 다음 범위
- MFA, 비번 주기 만료, SSO/외부 IdP, 복수 역할

## 흐름

### 0. 사전 (최초 1회)

- 최초 관리자 1명은 발급 흐름을 거치지 않고 Flyway 마이그레이션으로 DB에 심는다
  (첫 발급자가 없으므로). 비번 해시도 함께 심어 바로 로그인 가능하게 한다.

### 1. 발급 (관리자)

1. 관리자가 신규 사원 정보 입력: **사번 + 이메일 + 이름 + 역할**
2. 검증: 이메일이 허용 도메인인가 / 사번·이메일이 이미 쓰였나
3. 통과 시 `user_account` 생성 — `status = INVITED`, 역할 세팅, 비번은 비어 있음
4. 활성화 토큰(랜덤) 발급 → Redis 저장(TTL) → 그 이메일로 활성화 링크 발송

### 2. 활성화 (사원)

1. 사원이 메일의 링크 클릭 → 링크의 토큰으로 어느 계정인지 식별
2. 사원이 **비밀번호** 설정 → 해시 저장, `status = ACTIVE`
3. 활성화 토큰은 즉시 폐기(1회용)

### 3. 로그인 (사원)

1. 사원이 **사번 + 비밀번호**로 로그인 (`employee_no`로 계정 조회)
2. 비번 해시 대조 성공 시 **Access(JWT) + Refresh** 발급
3. Access 토큰 claim: `sub`(user_account.id), `employeeNo`, `role`
4. Refresh 토큰은 Redis에 저장(TTL)

### 4. 토큰 재발급·로그아웃

- 재발급: 유효한 Refresh 제출 → 새 Access+Refresh 발급, **옛 Refresh 폐기(회전)**
- 로그아웃: 해당 Refresh를 Redis에서 삭제(즉시 무효화)

### 5. 검증 (gateway·서비스)

- gateway가 auth의 **JWKS 엔드포인트(`/.well-known/jwks.json`)에서 공개키를 받아 캐시**하고,
  Access 토큰 서명을 공개키로 검증(auth에 매 요청 묻지 않음). 키 교체 시 JWKS만 갱신
- admin 전용 API는 `role = ADMIN`인지 gateway와 auth 서비스에서 함께 확인

## 규칙 / 예외

- **키·서명**: Access는 비대칭키 **RS256**. auth만 개인키로 서명, 검증 측은 공개키만 가진다.
  (검증이 서명보다 압도적으로 잦은 사내 시스템에 RS256이 적합)
- **공개키 전달**: auth가 JWKS 엔드포인트(`/.well-known/jwks.json`)로 공개키를 공개한다.
  검증 측(gateway)이 받아 캐시한다. 키 회전이 쉽다.
- **로그인 ID**: 사번(`employee_no`). 이메일은 활성화 메일 발송·도메인 체크용 필수 컬럼이지만
  로그인에는 쓰지 않는다.
- **토큰 만료**: Access 15분, Refresh 14일, 활성화 토큰 24시간.
- **허용 도메인**: 설정값(`auth.allowed-email-domain`). 로컬·데모는 `gmail.com`, 운영은 회사 도메인.
  gmail 제한은 데모용 placeholder이며 실제 직원 증명이 아니다 (코드에 명시).
- **유일성**: `employee_no`, `email` 각각 유니크. 중복 발급 거절.
- **로그인 거절**: `INVITED`(미활성)·`DISABLED`(비활성) 계정은 로그인 불가.
- **활성화 토큰**: 만료·재사용·없는 토큰은 거절. 재발급은 관리자가 다시 발송.
- **로그인 실패 잠금**: 비번 N회 연속 실패 시 일시 잠금(Redis 카운터). 무차별 대입 차단.
- **비밀번호**: 해시(BCrypt)만 저장. 평문·토큰 전체는 로그에 남기지 않는다(기획서 10.1).
- **역할**: 1인 1역할. 값 집합 `SALES, PURCHASE, PRODUCTION, WORKER, ADMIN`.
  **enum 컬럼으로 저장**(별도 role 테이블 없음).
- **진입점**: controller(HTTP) → service. Repository 직접 호출 금지.
- **X-User-Role 신뢰 전제 (보안)**: 서비스는 gateway 가 넘기는 `X-User-Role` 헤더로 ADMIN 여부를
  판단한다(방어 심층). 이 신뢰는 다음 두 가지가 모두 성립할 때만 유효하다.
  1. 서비스는 gateway 를 통해서만 접근 가능(네트워크 격리: ECS 보안그룹에서 인터넷 직접 접속 차단).
  2. gateway 가 클라이언트가 보낸 `X-User-*` 헤더를 **버리고(strip), 검증된 JWT 로 다시 채운다**.
  둘 중 하나라도 빠지면 클라이언트가 헤더를 위조해 우회할 수 있다(로컬에서 서비스를 직접 호출하면
  실제로 위조된다). 더 강한 보장이 필요하면 각 서비스가 헤더 대신 JWT 를 직접 검증(zero-trust)한다.

## 관련 이벤트 (events.md 참조)

- 없음. auth는 이벤트를 발행·수신하지 않는다 (services/auth/CLAUDE.md와 일치).

## 결정 기록

1. **공개키 전달**: JWKS 엔드포인트. (키 회전 용이)
2. **로그인 ID**: 사번(`employee_no`).
3. **role 저장**: enum 컬럼. 기획서는 `role` 테이블이나, 고정 5역할·1인1역할이라 단순화.
   복수 역할이 필요해지면 `role` 테이블 + 매핑으로 전환.
4. **토큰 만료**: Access 15분 / Refresh 14일 / 활성화 24시간.

## 다른 서비스에 필요한 후속 변경 (auth 범위 밖, 추후 상의 필요)

고객이 로그인하지 않기로 정함에 따라(사내 B2B), auth가 쥐고 있던 고객 로그인 계정이 사라진다.
그 여파로 다음이 필요하다.

- gateway 배선: 라우트 테이블(5개 서비스) + **신원 헤더 전달**. 이때 gateway 는 들어온 `X-User-*`
  헤더를 **반드시 버리고(strip)** 검증된 JWT 로 `X-User-Id`/`X-User-Role` 를 다시 채워야 한다.
  (이게 빠지면 위 "X-User-Role 신뢰 전제"가 깨져 운영에서도 역할 위조가 가능하다.)
- order 서비스에 **거래처 마스터 테이블** 신설, `customer_order.customer_id` 재연결
- saga 명세의 "고객이 취소 요청" → "판매 담당이 거래처 주문을 취소 요청"으로 문구 수정
- services/auth/CLAUDE.md의 `customer`/`admin` 설명을 `user_account`/`role`로 갱신

## 완료 조건 (테스트로 확인할 것)

- [ ] 관리자 발급 시 `INVITED` 생성 + 활성화 토큰 발행. 허용 도메인 아니면 거절
- [ ] 중복 사번/이메일 발급 거절
- [ ] 유효 토큰으로 활성화 시 비번 설정 + `ACTIVE`. 만료·재사용 토큰은 거절
- [ ] `INVITED`·`DISABLED` 계정 로그인 거절
- [ ] 올바른 자격증명 로그인 시 Access(RS256)+Refresh 발급, Access claim에 `role` 포함
- [ ] 비번 N회 실패 시 일시 잠금
- [ ] Refresh 재발급 시 새 쌍 발급 + 옛 Refresh 무효(회전), 로그아웃 시 Refresh 무효
- [ ] 공개키로 Access 서명 검증 성공
- [ ] `role != ADMIN` 토큰으로 admin API 호출 시 403
- [ ] 비번은 해시로 저장되고, 평문·토큰이 로그에 남지 않음
